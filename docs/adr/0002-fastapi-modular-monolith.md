# ADR 0002 — FastAPI as a modular monolith

- Status: Accepted
- Date: 2026-10-13

## Context

The mentor grades quizzes, schedules reviews, scores mastery, runs a restricted Python lab, ingests documents, and calls language models. Those behaviours share one learner record. The original brief asked for agents, clean architecture, dependency injection, and a separate backend process.

## Problem

Choose an API style and a process boundary that keep teaching rules testable and stop a network hop from appearing between “grade this quiz” and “update mastery.”

## Decision

One FastAPI application on Python 3.12 is the mentor. Layout:

| Layer | May do | May not do |
| --- | --- | --- |
| `app/domain` | Pure teaching rules | Import FastAPI, SQLAlchemy, or an HTTP client |
| `app/models` | Declare tables | Decide a grade or a recommendation |
| `app/repositories` | Query and persist | Call a model provider |
| `app/services` | Use cases, including the mentor engine | Embed pedagogy that belongs in `domain` |
| `app/agents` | Phrase a turn inside a policy result | Invent an answer key or execute code |
| `app/api` | Validate, authenticate, map status codes | Choose the next concept |

FastAPI `Depends` is the composition root. Sync SQLAlchemy 2 sessions back the engine. CQRS is limited to read models such as the dashboard and mastery. There is no event store and no message bus.

OpenAPI is generated by FastAPI at `/docs` and `/openapi.json`.

## Alternatives considered

| Alternative | Why it lost |
| --- | --- |
| A service per agent | Tutor, quiz, and mastery would each hold a partial learner. Every chat turn would be a distributed transaction. |
| Django | Admin and ORM are strong. The project already standardised on explicit Pydantic bodies and a thin router. Django’s admin is not the content workflow we need. |
| Node on the same Next.js server | The lab, parsers, and scientific Python stack belong next to the mentor. Splitting them into serverless functions fights the sandbox. |
| A separate DI container | `Depends` already constructs the engine per request. A second container would duplicate that graph. |

## Trade-off analysis

A modular monolith keeps a quiz grade, an XP grant, and a mastery recompute in one database transaction. Tests cover `app/domain` without a server, and the coverage gate is 90 percent on that package. The API process is also the thing that forks the lab interpreter, so a replica that is busy running student code is busy serving chat. That coupling is accepted until the runner moves to its own pool. See ADR 0006.

Sync routes run in a thread pool. The sandbox therefore applies resource limits inside the child process. `preexec_fn` deadlocks that thread pool and is rejected.

Domain coverage does not measure the engine or the routers. Integration tests cover the HTTP behaviour. A green domain percentage is not a claim about the whole process.

## Consequences

- New teaching behaviour lands in `app/domain` first, with a unit test, then the engine calls it.
- Agents are classes behind the engine, not deployable units. See ADR 0010.
- Ingestion is synchronous and capped at 10 MB. There is no Celery.
- One image is the release artifact. Horizontal scale is a replica of this process, with the rate-limiter consequence in ADR 0006.

## Future considerations

- Move document ingestion to a queue when uploads start occupying request workers.
- Move the code runner off the API replica before the replica cap of four is a product limit.
- Add an OTLP exporter. Tracing failures must continue to leave the request unaffected.
